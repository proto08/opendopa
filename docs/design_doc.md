## 1. 概要と背景

OpenDopaは、Project LINKS が公開する構造化オープンデータの CSV 1 行を、ニュース風の原稿・音声・縦型ショート動画に変換して見せるネタアプリである。

国土交通省は、文章などの非構造化データを手間をかけて構造化データにしている。本アプリはその逆、つまり構造化データを非構造化の文章へ戻すことを遊びにする。
ユーザーは何も選ばず、縦スクロールのショート動画を見るだけでよい。気に入ればいいねを押せる。見た時間が長い動画やいいねした動画に近い動画ほど、次に出やすくなる。

- 位置づけ: Web アプリ。公式の情報提供サービスではない。
- 最初の題材: 無人航空機の事故等報告(CSV)。「事故データ 1 行を、ニュース風の動画で見る」という当初の想定に最も合う。
- 体験の核: ユーザーは CSV もカテゴリも選ばない。入力は閲覧時間といいねだけで、動画のベクトルから作る「好みのベクトル」が動き、近い動画が出やすくなる。その好みは画面の右側に見える形で出る。
- 見た目: ニコニコ動画風の UI と機能(動画に流れるコメント)を意識する。
- 狙い: オープンデータに触れるハードルを下げ、数字の羅列を見物に変える。

## 2. ゴールと非ゴール

ゴールは「開いて見るだけで、ニュース風のショート動画が連続で流れ、閲覧時間といいねに合わせて好みが育ち、それが見える」こと。正確さを保ったまま、見て楽しいものにする。

**ゴール**

- CSV 1 行から、原稿・音声・縦型動画をバッチで自動生成する。
- 原稿には元の行にない事実を入れない。数字は元の行と機械的に照合する。
- ユーザーの入力は閲覧時間といいねだけにする。動画の内容をベクトル(埋め込み)にし、見た時間といいねから作る「好みのベクトル」に近い動画を次に出す。
- 好みのベクトルを、画面の右側に人が読める形で表示する(地図上の現在地、カテゴリ別の割合、一言の要約、視聴の記録)。
- MVP はショート動画のフィード。追加機能として、ニコニコ動画風にコメントが流れる動画を作る。
- データ種別の追加は、プロンプトテンプレートと列定義の追加だけで済むようにする。

**非ゴール**

- 事故の原因分析や、安全対策を促す公式な情報提供。
- ユーザーが見る瞬間に動画を生成すること(事前生成してキャッシュする)。
- 生成 AI での写実的な映像生成。映像はテロップ・地図・数字のアニメーションなど、コードで組める範囲にとどめる。
- ユーザーによるカテゴリや CSV の選択、検索、コメント投稿、ログイン。入力は閲覧時間といいねだけにする。
- 他のユーザーのいいねの表示や、いいね数のランキング(好みは本人にだけ見せる)。

## 3. ユーザー体験

ユーザーの操作は「開く」「縦にスクロールする」「いいねを押す」だけで、CSV もカテゴリも選ばない。入力として使うのは閲覧時間といいねだけである。

1. Web アプリを開くと、選択画面を挟まずにショート動画が再生される。
2. 縦スクロールで次の動画へ進む。1 本は 15〜30 秒
3. 各動画の視聴時間を記録する。見終わった動画の方向へ好みのベクトルを近づけ、すぐ飛ばした動画からは遠ざける。
4. いいねを押すと、その動画の方向へ好みがより強く動く。もう一度押すと取り消せる。
5. 画面の右側(スマホでは「好み」ボタンから開くシート)に、いまの好みが見える形で表示され、見るたび・いいねのたびに動く。

UI はニコニコ動画風を意識する。

### レコメンドの考え方

入力は閲覧時間といいねだけで、ログインも設定も要らない。

- 動画 1 本ごとに、原稿から埋め込みベクトルを作る(バッチ)。
- ユーザーごとに「好みのベクトル」を 1 本持つ。最初は空で、最初の数本は全カテゴリからランダムに出す。
- 動画から離れる時点の視聴率(視聴した時間 ÷ 動画の長さ)に応じて、好みのベクトルをその動画へ近づける。すぐ飛ばした場合は遠ざける。
- いいねは視聴率より強い信号として、その動画へ好みを近づける。取り消すと元に戻す。
- 次の動画は、好みのベクトルに近い動画を近傍検索して選ぶ。見た動画は除く。
- 偏りすぎないよう、好みから遠い動画も一定の割合で混ぜる(探索枠)。
- 閲覧履歴といいねは匿名の ID にだけ紐づけ、個人は特定しない。

視聴率の定義、いいねの重み、探索枠の割合は未決事項(§12)とする。

### 好みの表示(右側)

好みのベクトルは数字のままでは読めないため、人が読める形にして画面の右側に常時出す(スマホでは「好み」ボタンから開くシート)。次の 4 つを出す。

1. 動画を 2 次元に並べた地図と、その上の「いまの好み」の位置、見た動画、再生中の動画。
2. カテゴリ(クラスタ)ごとの好みの割合。
3. 好みを一言にまとめた要約。
4. 最近の視聴の記録。各動画が出た理由(好みに近い / 冒険枠 など)、視聴率、いいねの有無。

地図の座標とクラスタ名はバッチで作って保存し、閲覧時には計算しない。「いまの好み」の位置は、見た動画の座標を視聴率といいねで重み付けして、ブラウザ側で動かす。2 次元への変換は近似なので、本物のベクトルの位置とは少しずれる。

## 4. システム構成

CSV は取り込み後に、原稿生成、数値検証、埋め込みと地図の座標の計算、音声・動画の順で処理する。数値が元の行と合わなければ原稿を作り直す。ユーザーに届くのは完成済みの動画だけで、閲覧時には何も生成しない。閲覧時間といいねだけがフィード API に戻り、ユーザーの好みのベクトルを更新して、次に出す動画を決める。

## 6. データモデル

元データの行と、生成物(原稿・音声・動画)を必ず 1 対 1 でひも付ける。これが検証と「元データへ戻る」機能の土台になる。

| テーブル | 主なカラム | 役割 |
| --- | --- | --- |
| datasets | id, 名称, 元データの URL, ライセンス表記, 取り込み日 | データ種別(= カテゴリ)のマスタ |
| source\_rows | id, dataset\_id, 行番号, 元行の JSON, 行ハッシュ | CSV 1 行をそのまま保存する |
| scripts | id, source\_row\_id, 原稿, プロンプト版, 検証結果 | 生成したニュース原稿 |
| videos | id, script\_id, 音声 URL, 動画 URL, 長さ, 種別(ショート/動画), 生成日時 | 完成した動画 |
| feed\_items | id, dataset\_id, video\_id | 配信できる動画の一覧(表示順は好みのベクトルから都度決める) |
| view\_events | id, 匿名 ID, video\_id, dataset\_id, 視聴時間, 日時 | 閲覧時間の記録。好みのベクトルを動かす入力の一つ |
| like\_events | id, 匿名 ID, video\_id, dataset\_id, 日時, 取り消し済みか | いいねの記録。好みのベクトルを動かす入力の一つ |
| embeddings | video\_id, ベクトル, 地図の座標(x, y), クラスタ ID, クラスタ名, モデル版 | 動画ごとのベクトルと、右側の地図に出す座標。バッチで作る |
| user\_vectors | 匿名 ID, 好みのベクトル, 更新日時 | ユーザーごとの好み。見るたび、いいねのたびに更新する |
| comments(追加機能) | id, video\_id, 動画内の時刻, 本文 | バッチで生成した流れるコメント |

カラムは取り込む CSV ごとに異なるため、source\_rows は列を固定せず JSON で持つ。データ種別ごとの違いは、列の説明とプロンプトテンプレート(§7)に集める。

## 7. 原稿生成と検証

原稿は LLM が 1 行を読んで書くが、元の行にない事実は一切書かせない。そのため生成と検証を分ける。

**プロンプト方針**

- 入力は「列名と値の組」だけ。列の説明はデータ種別ごとに用意する。
- 「列の値にあることだけを述べる。原因・責任・被害の推測は書かない」を明記する。
- 出力は JSON(原稿、テロップ、原稿中で使った数字の一覧)とする。
- トーンはニュース番組風。事故系データは落ち着いた語り口にする。

**検証(生成後に機械的に実行)**

1. 原稿に出てくる数字・日付・地名が、元の行の値と一致するかを確かめる。
2. 不一致があれば再生成する。規定回数で失敗した行はスキップして記録する。
3. 個人を特定できる情報(氏名、詳細な住所など)が列にあれば、原稿に含めない。

この検証の結果は scripts テーブルの「検証結果」に保存する。

## 8. 音声・動画生成

動画は「動画生成 AI」ではなく、コードで組むテンプレートと TTS(音声合成)で作る。理由は、費用と時間が小さく、表示する数字が元データどおりになるから。

- 音声: 原稿を TTS で読み上げ、音声ファイルと長さを保存する。
- 映像: ニュース番組風のテンプレート(タイトル、テロップ、数字、簡単な地図)を、コードから動画に書き出す(例: Remotion)。
- 形式(MVP のショート): 縦型(9:16)、長さ 30〜60 秒。
- 事前生成: バッチで作ってストレージに置き、フィードは完成済みの動画を並べるだけにする。
- 人物の扱い: 実在の人物の顔は映像に出さない。アナウンサーはイラストやアイコンにする。

動画の作り方の具体的な選定(TTS の種類、動画ライブラリ)は未決事項として §12 に記載する。

追加機能の動画(ショートより長い横型を想定)も、同じバッチで事前に作る。ニコニコ動画風に、コメントが動画の上を右から左へ流れる。コメントも事前バッチで、動画内の時刻つきで生成して保存する。ユーザーはコメントを投稿しない(入力は閲覧時間だけ)。

## 9. フロントエンド

フロントエンドは Web アプリで、ニコニコ動画風の見た目と操作感を意識する。MVP の画面は、縦スクロールのフィードと、その右側の好みの表示(スマホでは開閉するシート)にする。

- **縦スクロールのフィード**: 1 画面 1 動画。開いた瞬間に再生し、スワイプやスクロールで次へ進む。
- **閲覧時間の計測**: 表示中の動画の視聴時間を測り、次の動画へ移る時点でフィード API へ送る。
- **いいね**: 各動画にいいねボタンを置く。押すと好みのベクトルがその動画の方向へ動き、もう一度押すと取り消せる。
- **好みの表示**: 画面の右側に、「好みの表示(右側)」の 4 つを出す。

各動画には次の表示を常に出す。

1. 「AI 生成のフィクション風解説」というラベル。
2. 元データの名称、行番号、元データへのリンク。
3. 元の CSV 行を展開して見られるボタン(どこからこの原稿ができたかの確認用)。

ログインは不要にし、ユーザーは匿名の ID(ブラウザに保存)だけで識別する。API は「次の動画を返す」「閲覧時間を受け取る」「いいねを受け取る」の 3 本にする。好みのベクトルは、匿名 ID に紐づけてサーバー側に持つ。

**追加機能: 動画とコメント**

- 横型の動画ページを追加し、MVP のショートとは別の画面にする。
- コメントは動画の再生時刻に合わせて、画面の右から左へ流れる。
- コメントはバッチで生成した固定データを表示するだけで、投稿 UI は作らない。

## 10. MVP計画

MVP は 08 の事故等報告だけで、ショート動画の生成と、ベクトルによるレコメンド(閲覧時間といいね)、右側の好みの表示までを通して試す。追加機能の動画とコメントは、MVP の次のフェーズにする。種別の追加は、検証で数値が合うことを確かめてから、プロンプトテンプレートと列定義を足す形で進める。日程は未定のため、フェーズの順番だけを示している。

- [ ] TTS の種類(音質・料金・日本語の読みの精度)
- [ ] 動画をコードから作るライブラリ(Remotion を候補とする)
- [ ] 埋め込みモデルと、地図用の 2 次元の作り方(UMAP か PCA か)
- [ ] 視聴率といいねの重み、好みの更新式(近づく量、飛ばしたときに遠ざかる量)
- [ ] クラスタの数と名前の付け方(LLM で命名する案)
- [ ] 好みから遠い動画を混ぜる割合(固定にするか、バンディットで自動調整するか)

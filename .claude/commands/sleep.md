# 一括自動実装(sleep)

引数: `$ARGUMENTS`(イシュー番号。省略可。複数可)

`/start-task` とほぼ同じ作業を、**ユーザーに一切確認せず**に実行する。ユーザーは不在(寝ている)ものとして、判断はすべて自分で行い、最後に結果を報告する。

このファイルは**親(オーケストレーター)の手順だけ**を書く。各作業の詳細は役割別のファイルにあり、**サブエージェントには該当ファイル1つだけを読ませる**(全体を読ませない。トークンの節約)。

| 役割 | ファイル |
| --- | --- |
| レビュー(他の人のPR。指摘なしならマージ) | `.claude/sleep/review.md` |
| マージ確認(自分がレビュー済みのPR) | `.claude/sleep/merge-check.md` |
| コンフリクト解消(自分のPR) | `.claude/sleep/conflict.md` |
| 実装・レビュー対応(イシュー) | `.claude/sleep/implement.md` |
| 共通規則(マージ・レビュー観点・決定の記録) | `.claude/shared/*.md` |

## 原則

- **質問しない・許可を待たない**。`AskUserQuestion` は使わない。迷ったら、安全側(破壊的でない・外部に影響しない側)を選び、その判断を最終報告に書く。
- 投稿してよいのは、(a) 自分のPRへのレビュー対応報告、(b) 他の人のレビュー待ちPRへのレビュー、(c) 自分がレビューしたPRの対応確認結果、(d) 自分のPRのコンフリクト解消の報告、の4つだけ。それ以外のPR・イシューへは投稿しない。
- マージしてよいのは、次の3つだけ。それ以外のPRはマージしない。
  - 自分がレビューしたPRで、指摘の対応を確認でき、マージ可能と判断したもの(`merge-check.md`)。
  - 自分がレビューして「指摘なし」だったPRで、マージ条件を満たしたもの(`review.md`)。
  - コンフリクトを自分で解消して push した自分のPRで、マージ条件を満たしたもの(`conflict.md`)。コンフリクトと無関係の自分のPR(レビュー待ち、指摘対応中など)はマージしない。
- **状態ラベル**(`status::*`。定義・遷移・掃除は `docs/kanban.md`)の付け替えは、投稿に数えない。他の人のPRにも行ってよい。作業を終えるとき(成功・失敗・中断のどれでも)、自分が付けた作業中のラベルを必ず外すか次の状態に付け替える。
- 破壊的な操作(force push、他人のブランチの書き換え、未pushの変更を含むworktreeの削除、ブランチの削除、イシューのクローズ・編集)はしない。
- 他の人が担当のイシュー、「他の人待ち」のイシューは実装しない。

## サブエージェントの起動規約

- プロンプトは**短く**する。含めるのは、(1) 役割ファイルのパス(「`.claude/sleep/<役割>.md` を読んで、その手順を実行せよ」)、(2) 対象(PR番号 / イシュー番号とモード)、(3) 原則の要約(質問しない・破壊的操作をしない・投稿してよい範囲)、(4) 報告は役割ファイルの「返す報告」の形で短く、の4つだけ。手順を親が書き写さない。
- **モデル**: 判断の軽い定型作業(`merge-check`)は、親より軽いモデルを `model` で指定してよい(親がすでに軽いモデルなら指定しない)。`review`・`implement`・`conflict` は指定せず、親と同じモデルで動かす。
- **同時実行は最大4つ**。バッチではなく**ローリング**で回す: 空きができる(完了通知を受ける)たびに、待機中の次の対象をすぐ起動する。遅い1つのために空きを遊ばせない。
- **起動順**: 長い `implement` を先に起動し、そのあとに `review`・`merge-check`・`conflict` を起動する。マージで前提が解消されたイシューは、**次のラウンド**で扱う(同じラウンドでは着手しない)。

## 0. ラウンドのループ

### 0a. main の最新化(各ラウンドの最初)

メインの作業ディレクトリで main を最新にする。

- `git status --porcelain` と `git branch --show-current` を確認する。
- 現在のブランチが main で、未コミットの変更がなければ `git pull --ff-only origin main` を実行する。
- main 以外、または未コミットの変更がある場合は、`git checkout` / `git switch` をせず `git fetch origin` だけを行う。この場合は**最終報告に1回だけ**「main を更新できなかった(理由)」と書く(ラウンドごとには書かない)。コマンド定義(`.claude/`)を編集した直後は、未コミットのため pull されないことが多い。
- `--ff-only` で失敗した場合は、無理に merge / reset せず、その旨を最終報告に書いて続行する。
- pull で `.claude/commands/` や `.claude/sleep/` の内容が**実際に変わった**ときだけ、変わったファイルを読み直す。変わっていなければ読み直さない。
- **最初のラウンドだけ**、`docs/kanban.md` の「残骸の掃除」に従い、自分が付けて残っている作業中の状態ラベルを外す。他の人が付けたラベルには触れない。

### 0b. 終了条件

手順 1〜3 を **1ラウンド** とする。次のいずれかになったら、ループを終えて手順 4 の最終報告をする。

- **対象が完全になくなった**: 手順 1 で、レビュー対象・マージ確認の対象・コンフリクト対象・実装対象のすべてが0件。
- **次のラウンドで新しい対象が出る見込みがない**: ラウンド終了時点で、**このラウンドでマージが1件もなかった**。
  - 新しい対象が生まれるのは、main が進んだとき(前提イシューの解消、他のPRのコンフリクト、など)だけ。
  - レビューの投稿・PR作成・push だけでは、作成者が不在の間は何も変わらない。自分で作ったPRは、レビュー対象にもマージ対象にもならない(コンフリクト解消後のマージを除く)。
  - したがって、それらだけのラウンドの次に、同じ全件取得を繰り返しても必ず空振りになる。
- **ラウンド数の上限**: 10ラウンドに達した。上限で止まった場合は、その旨と残っている対象を最終報告に書く。

マージが1件以上あれば、手順 0a に戻って次のラウンドを実行する(他の人のPRのマージで前提が解消されたイシューも、次のラウンドで実装対象になる)。

### 0c. 状態ファイル(コンテキストに頼らない)

ラウンド数・対応済み・失敗の記録は、コンテキストが要約されても失われないよう、**スクラッチパッドディレクトリ**(システムプロンプトで指定された、このセッション専用のディレクトリ)の `sleep-state.json` に書く。git 管理下には置かない・commit しない。

```json
{
  "round": 2,
  "reviewed": [{"pr": 12, "headSha": "abc123", "merged": false}],
  "merge_checked": [{"pr": 9, "headSha": "def456", "merged": false}],
  "merged": [7],
  "created": [{"issue": 30, "pr": 41}],
  "conflict_resolved": [{"pr": 41, "headSha": "789abc", "merged": true}],
  "conflict_unresolved": [{"pr": 43, "headSha": "456def", "reason": "双方の意図が両立しない"}],
  "ci_pending": [{"pr": 15, "headSha": "aaa111"}],
  "failed": [{"issue": 31, "reason": "テストが通らない"}],
  "skipped": [{"issue": 35, "reason": "他の人待ち(#34 / @someone)"}],
  "issue_requires": {"30": {"updatedAt": "2026-11-04T10:00:00Z", "requires": [34, 38]}}
}
```

- 最初のラウンドの開始時にファイルがなければ作る(`round: 0`)。あれば読み込む(要約後の再開を含む)。
- 各ラウンドの開始時に読み、手順 1 の対象から次を除く。
  - `reviewed` / `merge_checked` / `ci_pending` / `conflict_unresolved` にあるPRのうち、現在の head SHA が記録と同じもの(新しい commit がない。main が進んだだけでは再試行しない)。自分のコメントは「更新」に数えない。
  - `failed` のイシュー(再実行しない)。
- `issue_requires` は、イシュー本文の `前提:` 行の解析結果のキャッシュ。`updatedAt` が変わらないイシューは本文を取り直さない。前提がオープンかどうかは毎ラウンド確認する。
- サブエージェントの報告を受けるたびに、その結果をすぐ追記する(ラウンドの終わりまで待たない)。ラウンド数もここで数える。
- 最終報告はこのファイルの内容から作る。

## 1. 対象の特定

**出力は必要な項目だけに絞る**(`--jq` / `jq`)。レビュー本文やイシュー本文を全件、毎ラウンド取得しない。

### 1a. レビュー待ちPR

```bash
ME=$(gh api user --jq .login)
gh pr list --state open --limit 1000 \
  --json number,title,author,headRefName,headRefOid,isDraft,updatedAt,labels,reviews \
| jq --arg me "$ME" '[.[]
    | select(.author.login != $me and (.isDraft | not))
    | {number, title, author: .author.login, headRefOid, updatedAt,
       labels: [.labels[].name],
       myReviewAt: ([.reviews[] | select(.author.login == $me) | .submittedAt] | max)}]'
```

各PRを次のように分ける。

- **レビュー対象**: `myReviewAt` が null(まだ自分がレビューしていない)。→ `review.md`
- **マージ確認の対象**: `myReviewAt` があり、`updatedAt` がそれより新しい(その後に commit やコメントがある)。→ `merge-check.md`
- **対象外**: 自分がレビュー済みで、その後の更新がない。

ラベルに `status::pr-review` または `status::merge-check` があり、`docs/kanban.md` の「他の人の作業中を避ける」の判定で他の人が作業中のものは、このラウンドの対象から外す(報告に書く)。

### 1b. 実装対象イシュー

1. 自分が担当のオープンなイシューを、本文なしで取得する。
   `gh issue list --state open --assignee @me --limit 1000 --json number,title,labels,updatedAt`
   - `type::tracking` ラベルのものは除く。
   - 0件なら、担当者のいないイシューは**実装しない**。その旨を記録し、実装側は行わない(他は続ける)。
2. 本文は、`issue_requires`(手順 0c)にない、または `updatedAt` が変わったイシューだけ `gh issue view <番号> --json body --jq .body` で取得する。`前提: #34、#38、...` の行から前提を抜き出してキャッシュする(`親イシュー:` は依存ではない)。
3. 前提のオープン判定は1回で行う。
   `gh issue list --state open --limit 1000 --json number,assignees`
   これと突き合わせて、各イシューを分類する。
   - **着手可能**: 前提がすべてクローズ済み。
   - **自分の前提待ち**: オープンな前提がすべて自分の担当。
   - **他の人待ち**: オープンな前提に、他の人が担当、または担当者なしのものがある。
4. **対象は「着手可能」なものすべて**。引数で番号が指定されたときは、そのうち「着手可能」なものだけ(前提が未完了のものは対象外にして報告に書く)。
5. 「着手可能」以外は、待っている前提と担当者を状態ファイルの `skipped` に記録する。
6. 対象の一覧(番号・タイトル・分類)を表示してから、そのまま続行する。

対象ごとに、対応するオープンなPRを探す。
`gh pr list --state open --limit 1000 --json number,headRefName,closingIssuesReferences`
(この結果は 1c でも使うので、1回の取得を使い回す。)

- PRがあり、レビューが投稿されている(`gh pr view <番号> --json reviews,comments` と `gh api repos/{owner}/{repo}/pulls/<番号>/comments`) → **レビュー対応モード**。
- PRがあり、レビューがない → すでに対応中なので**スキップ**する(報告に書く)。
- PRがない → 通常モード。

### 1c. コンフリクトしている自分のPR

`gh pr list --state open --author @me --limit 1000 --json number,title,headRefName,headRefOid,mergeable` で、`mergeable` が `CONFLICTING` のものを集める(他の人のPRは対象外)。`UNKNOWN` は少し待って1回だけ取り直し、それでも `UNKNOWN` ならこのラウンドでは対象外にする。→ `conflict.md`

1b のレビュー対応モードの対象PRは、`implement.md` の中でコンフリクトも解消する。同じPRを `conflict.md` と `implement.md` で二重に起動しない(レビュー対応モードで処理するPRは 1c から除く)。

## 2. 並列で実行

「サブエージェントの起動規約」に従って、対象ごとにサブエージェントを起動する。

- `implement` ← 1b の対象イシュー(モードも渡す)
- `review` ← 1a のレビュー対象PR
- `merge-check` ← 1a のマージ確認の対象PR
- `conflict` ← 1c の対象PR

同じファイル(`docs/DECISIONS.md` の末尾など)を複数のサブエージェントが編集して、マージ時に衝突しうることは想定済み。衝突は後でマージする人が解決するので、事前に調整しようとしない。ただしその旨を最終報告に書く。

## 3. 後片付け(各ラウンドの最後)

全サブエージェントの完了後、確認なしで次を行う。

- レビュー用 worktree は各担当が削除済みのはずなので、残っていれば報告する。
- 実装用 worktree: 変更がすべて commit・push 済み(`git -C ../opendopa-<番号> status --porcelain` が空で、`git log origin/<ブランチ名>..HEAD` も空)のものだけ `git worktree remove ../opendopa-<番号>` で削除する。そうでないものは残し、報告に書く。
- 実装中に起動した捨て docker コンテナ・ボリューム・ネットワークのうち、サブエージェントが自分で起動したと報告したものだけ削除する。それ以外には触れない。
- ブランチは削除しない(PR が参照している)。

## 4. 最終報告

全ラウンド分をまとめて**1回だけ**、ユーザーが朝に読む前提で簡潔に書く(状態ファイルから作る)。表は、該当がある場合だけ載せる。

- レビューした PR の表(PR の URL・作成者・指摘の要約・総評・「指摘なし」でマージしたか、しなかった理由)
- マージ確認した PR の表(PR の URL・作成者・各指摘の対応状況・マージしたか、しなかった理由)
- 作成・更新した PR の表(イシュー番号・PR の URL・モード・テスト結果)
- コンフリクトを扱った自分の PR の表(PR の URL・コンフリクトしたファイル・解消方針・push したか・マージしたか、解消できなかった理由・マージしなかった理由)
- スキップ・対象外にしたイシューとその理由(待っている前提と担当者、既存PRで対応中、CI待ちで見送り、など)
- 質問せずに自分で判断した点
- 未解決事項、残した worktree、マージ時に衝突しそうな箇所
- 次にやるとよいこと(今回の PR がマージされると着手可能になるイシューなど)

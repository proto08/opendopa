# 一括自動実装(sleep)

引数: `$ARGUMENTS`(イシュー番号。省略可。複数可)

`/start-task` とほぼ同じ作業を、**ユーザーに一切確認せず**に実行する。ユーザーは不在(寝ている)ものとして、判断はすべて自分で行い、最後に結果を報告する。

**ループは止めない。ただし、対象がない回は、ほぼトークンを使わずに終える。** 「何をやるか」の判定は、機械的なスクリプト(`sleep-scan`)が行い、LLM は対象があるときだけ働く。

このファイルは**親(オーケストレーター)の手順だけ**を書く。各作業の詳細は役割別のファイルにあり、**サブエージェントには該当ファイル1つだけを読ませる**(全体を読ませない)。

| 役割 | ファイル |
| --- | --- |
| レビュー(他の人のPR。指摘なしならマージ) | `.claude/sleep/review.md` |
| マージ確認(自分がレビュー済みのPR) | `.claude/sleep/merge-check.md` |
| コンフリクト解消(自分のPR) | `.claude/sleep/conflict.md` |
| 実装・レビュー対応(イシュー) | `.claude/sleep/implement.md` |
| ハーネス自身の修復(PR 方式・セルフレビュー・触ってよい範囲) | `.claude/shared/harness-repair.md` |
| 共通規則(マージ・レビュー観点・決定の記録・REST の操作) | `.claude/shared/*.md` |

## 原則

- **ハーネス(この手順書・`sleep-scan` など)の不具合や改善点は、自分で直す**(ユーザー承認済み)。手順、触ってよい範囲、セルフレビューは `.claude/shared/harness-repair.md` に従う。この修復の PR 作成とマージは、下の投稿(e)とマージ(4)の枠で行う。
- **質問しない・許可を待たない**。`AskUserQuestion` は使わない。迷ったら、安全側(破壊的でない・外部に影響しない側)を選び、その判断を最終報告に書く。
- 投稿してよいのは、(a) 自分のPRへのレビュー対応報告、(b) 他の人のレビュー待ちPRへのレビュー、(c) 自分がレビューしたPRの対応確認結果、(d) 自分のPRのコンフリクト解消の報告、(e) ハーネス修復のPRの作成、の5つだけ。それ以外のPR・イシューへは投稿しない。
- マージしてよいのは、次の4つだけ。それ以外のPRはマージしない。
  - 自分がレビューしたPRで、指摘の対応を確認でき、マージ可能と判断したもの(`merge-check.md`)。
  - 自分がレビューして「指摘なし」だったPRで、マージ条件を満たしたもの(`review.md`)。
  - コンフリクトを自分で解消して push した自分のPRで、マージ条件を満たしたもの(`conflict.md`)。
  - 自分で作ったハーネス修復のPRで、セルフレビューが指摘なしで、マージ条件を満たしたもの(`harness-repair.md`)。
  - 自分のPRは、上の3つ目と4つ目以外では**マージしない**。`status::ready-to-merge` が付けば、GitHub が自動でマージする(`.claude/shared/merge-rules.md`「自分の PR の自動マージ」)。
- **状態ラベル**(`status::*`)と `needs-human`(定義・遷移・掃除は `docs/kanban.md`)の付け替えは、投稿に数えない。他の人のPRにも行ってよい。作業を終えるとき(成功・失敗・中断のどれでも)、自分が付けた作業中のラベルを必ず外すか次の状態に付け替える。
- 破壊的な操作(force push、他人のブランチの書き換え、未pushの変更を含むworktreeの削除、ブランチの削除、イシューのクローズ・編集)はしない。
- 他の人が担当のイシュー、「他の人待ち」のイシューは実装しない。
- GitHub の操作は **REST(`gh api`)だけ**を使う(`.claude/shared/github-rest.md`)。`gh pr ...` / `gh issue ...` はこの環境で 403 になる。

## 1. 対象を洗い出す(これが最初で、LLM を使わない)

```bash
mise run sleep-scan      # mise がなければ: bash mise-tasks/sleep-scan
```

JSON が1つ出る。`idle`、`fingerprint`、`targets`(review / merge_check / conflict / review_fix / implement)、`waiting`(needs_human / blocked_issues / merge_candidates / busy)。

- **`idle` が `true` なら、`idle(指紋 <fingerprint>)` と1行だけ書いて終わる。** 手順書の他の部分も、役割ファイルも読まない。`git fetch` もしない。ループの次の回は、呼び出し元(予約やイベント)に任せる。
- 引数でイシュー番号が指定されたときは、`implement` のうち、その番号だけを対象にする(他の対象は扱わない)。
- `sleep-scan` は、状態ファイルを持たない。対応済みかどうかは、GitHub 上の「自分の最後の活動」と「他の人の最後の活動」を比べて決まる。そのため、各担当は、**終えたあとに同じ対象が残らない**ようにする(各役割ファイルの「終わり方」)。

### 最初の回だけ(`idle` でない回の最初)

`docs/kanban.md` の「残骸の掃除」に従い、自分が付けて残っている作業中の状態ラベルを外す。他の人が付けたラベルには触れない。

## 2. 並列で実行

`idle` が `false` のときだけ行う。`git fetch origin` を1回してから、対象ごとにサブエージェントを起動する。

- `implement` ← `targets.implement`(通常モード)と `targets.review_fix`(レビュー対応モード。コンフリクトも `implement.md` の中で解消する。`conflict` には渡さない)
- `review` ← `targets.review`
- `merge-check` ← `targets.merge_check`(軽いモデルを `model` で指定してよい)
- `conflict` ← `targets.conflict`

起動規約:

- プロンプトは**短く**する。含めるのは、(1) 役割ファイルのパス(「`.claude/sleep/<役割>.md` を読んで、その手順を実行せよ」)、(2) 対象(PR番号 / イシュー番号とモード)、(3) 原則の要約(質問しない・破壊的操作をしない・投稿してよい範囲・REST を使う)、(4) 報告は役割ファイルの「返す報告」の形で短く、の4つだけ。手順を親が書き写さない。
- **同時実行は最大4つ**。ローリングで回す: 空きができるたびに、待機中の次の対象をすぐ起動する。
- **起動順**: 長い `implement` を先に起動し、そのあとに `review`・`merge-check`・`conflict`。
- 同じファイルを複数のサブエージェントが編集して、マージ時に衝突しうることは想定済み。事前に調整しない。ただし最終報告に書く。

進捗表(実行中のタスクの可視化。`idle` の回は出さない):

| 役割 | 対象 | 状態 | 結果 |
| --- | --- | --- | --- |
| implement | #30 タイトル | 実行中 | |
| review | PR #12 タイトル | 待機 | |
| merge-check | PR #9 タイトル | 完了 | マージ済み |
| conflict | PR #41 タイトル | 失敗 | 双方の意図が両立しない |

- 列は上の4つ。状態は「待機 / 実行中 / 完了 / 失敗」。結果は完了・失敗のときだけ1行で書く(マージ済み、指摘N件、PR作成、失敗の理由、など)。
- 表の上に1行で `実行中 X / 4 ・ 待機 Y ・ 完了 Z ・ 失敗 W` と書く。
- 表示するのは、(1) 対象を洗い出した直後、(2) サブエージェントの完了通知を受けて次を起動するたび、(3) 回の終わり。表だけを出し、経過の説明は足さない。手順 4 の報告の表とは別物。

## 3. 回の終わり

全サブエージェントの完了後、確認なしで次を行う。

1. 後片付け:
   - 変更がすべて commit・push 済み(`git -C ../opendopa-<番号> status --porcelain` が空で、`git log origin/<ブランチ名>..HEAD` も空)の worktree だけ、`git worktree remove` で削除する。そうでないものは残して、報告に書く。
   - サブエージェントが自分で起動したと報告した docker 等だけ削除する。ブランチは削除しない。
2. もう一度 `sleep-scan` を実行する。
   - `idle` なら、手順 4 へ。
   - `idle` でなく、**前回と指紋が違う**(進んだ)なら、手順 2 に戻る。マージで前提が解消されたイシューも、ここで拾われる。
   - `idle` でなく、**指紋が前回と同じ**(何も進まなかった)なら、同じ対象に対して、役割ファイルの「終わり方」が守られていない。その対象には `needs-human` を付け(`docs/kanban.md`)、理由を報告に書いて、手順 4 へ。**同じ対象を2回続けて処理しない。**

## 4. 報告

**変わったことだけ**を、簡潔に書く。何もしなかった回は、手順 1 の1行だけ。

- レビュー・マージ確認・コンフリクト解消・作成・更新した PR の表(PR の URL、結果、マージしたか、しなかった理由、テスト結果)
- 質問せずに自分で判断した点
- **人の確認待ち**(`waiting.needs_human` と `waiting.merge_candidates`、`waiting.blocked_issues`)。前回の報告と同じものは、件数だけにする
- 残した worktree、マージ時に衝突しそうな箇所
- 次にやるとよいこと

## ループの回し方

止めるのは、ユーザーが「やめろ」と言ったときだけ。終了条件(マージ0件・ラウンド数の上限)は設けない。空回りのコストは、手順 1 の `idle` 判定で抑える。

- **推奨: イベントで起こす。** 自分のPRと、レビューしたPRに `subscribe_pr_activity` を使う。コメント・commit・CI があったときだけセッションが起きる。待っている間のトークンはゼロ。
- **保険: 60分ごとに `/sleep` を予約する。** 新しい PR・イシュー・main の更新は、`sleep-scan` が拾う。`idle` なら1行で終わるので、頻度を上げても高くない(20分でもよい)。
- 予約するのは、実行の最後(手順 4 のあと)。**`idle` の回でも、次の予約を忘れない。**

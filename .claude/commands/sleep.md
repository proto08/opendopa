# 一括自動実装(sleep)

引数: `$ARGUMENTS`(イシュー番号。省略可。複数可)

`/start-task` とほぼ同じ手順を、**ユーザーに一切確認せず**に実行する。ユーザーは不在(寝ている)ものとして、判断はすべて自分で行い、最後に結果を報告する。

## 原則

- **質問しない・許可を待たない**。`AskUserQuestion` は使わない。迷ったら、安全側(破壊的でない・外部に影響しない側)を選び、その判断を最終報告に書く。
- 投稿前の確認も行わない。投稿してよいのは、(a) 自分のPRへのレビュー対応報告、(b) 他の人のレビュー待ちPRへのレビュー、(c) 自分がレビューしたPRの対応確認結果、の3つだけ。それ以外のPR・イシューへは投稿しない。
- マージしてよいのは、次の2つだけ。それ以外のPRはマージしない。
  - **自分がレビューしたPRで、指摘の対応を確認でき、マージ可能と判断したもの**(手順 2c)。
  - **コンフリクトを自分で解消して push した自分のPRで、マージ条件(手順 2d)をすべて満たしたもの**。コンフリクトの指摘を受けた自分のPRは自分で直し、直したあとは自分でマージする。コンフリクトと無関係の自分のPR(レビュー待ち、指摘対応中など)は、これまでどおりマージしない。
- **状態ラベル**(`status::*`。定義・遷移・掃除は `docs/kanban.md`)の付け替えは、投稿に数えない。他の人のPRにも行ってよい。作業を終えるとき(成功・失敗・中断のどれでも)、自分が付けた作業中のラベルを必ず外すか次の状態に付け替える。
- 破壊的な操作(force push、他人のブランチの書き換え、未pushの変更を含むworktreeの削除、ブランチの削除、イシューのクローズ・編集)はしない。
- 他の人が担当のイシュー、「他の人待ち」のイシューは実装しない。

## 0. main の最新化とループ(最初に必ず実行)

### 0a. main の最新化

各ラウンドの開始時(手順 1 より前)に、メインの作業ディレクトリで main を最新にする。コマンド定義(`.claude/commands/`)も main に含まれるため、これで常に最新の手順で動く。

- `git status --porcelain` と `git branch --show-current` を確認する。
- 現在のブランチが main で、未コミットの変更がなければ `git pull --ff-only origin main` を実行する。
- 現在のブランチが main 以外、または未コミットの変更がある場合は、`git checkout` / `git switch` をせず、`git fetch origin` だけを行い、更新できなかった旨を最終報告に書く。
- `--ff-only` で失敗した場合は、無理に merge / reset せず、その旨を最終報告に書いて続行する。
- pull で `.claude/commands/` の内容が変わった場合は、このコマンドの定義(と `pr-review.md`・`start-task.md`)を読み直し、最新の内容に従う。
- **最初のラウンドの開始時だけ**、`docs/kanban.md` の「残骸の掃除」に従い、自分が付けて残っている作業中の状態ラベルを外す。他の人が付けたラベルには触れない。

### 0b. 対象がなくなるまでループ

手順 1〜3(対象の特定、並列実行、後片付け)を **1ラウンド** とし、ラウンドが終わるたびに、手順 4 の最終報告はせず、**手順 0a に戻って次のラウンドを実行する**。他の人のPRのマージで前提が解消されたイシューや、レビュー後に作成者が更新したPRが次のラウンドの対象になるため。

次のいずれかになったら、ループを終了して手順 4 の最終報告をする。

- **対象が完全になくなった**: ラウンドの手順 1a で、レビュー対象PR・マージ確認の対象PRが0件、かつ手順 1b で、実装対象(着手可能で、既存PRがレビュー待ちでもないもの)が0件。
- **進捗がなくなった**: 直前のラウンドで、レビュー投稿・マージ(コンフリクト解消後の自分のPRのマージを含む)・PR作成・PRへの push(コンフリクト解消の push を含む)のいずれも1つも行われなかった(同じ状態を繰り返して無限ループになるのを防ぐ。マージ確認でマージせずコメントしたPR、他の人待ちのイシューなどは、これで止まる)。
- **ラウンド数の上限**: 10ラウンドに達した。上限で止まった場合は、その旨と残っている対象を最終報告に書く。

### 0c. 状態ファイル(コンテキストに頼らない)

ラウンド数・対応済み・失敗の記録は、コンテキストが要約されても失われないよう、**スクラッチパッドディレクトリ**(システムプロンプトで指定された、このセッション専用のディレクトリ)の `sleep-state.json` に書く。git 管理下には置かない・commit しない。

```json
{
  "round": 2,
  "reviewed": [{"pr": 12, "headSha": "abc123"}],
  "merge_checked": [{"pr": 9, "headSha": "def456", "merged": false}],
  "merged": [7],
  "created": [{"issue": 30, "pr": 41}],
  "conflict_resolved": [{"pr": 41, "headSha": "789abc", "merged": true}],
  "conflict_unresolved": [{"pr": 43, "reason": "双方の意図が両立しない"}],
  "failed": [{"issue": 31, "reason": "テストが通らない"}],
  "skipped": [{"issue": 35, "reason": "他の人待ち(#34 / @someone)"}]
}
```

- 最初のラウンドの開始時にファイルがなければ作る(`round: 0`)。あれば読み込む(要約後の再開を含む)。
- 各ラウンドの開始時に読み、手順 1 の対象から次を除く。
  - `reviewed` / `merge_checked` にあるPRのうち、現在の head SHA が記録と同じもの(作成者の新しい commit がない)。
  - `failed` のイシュー(再実行しない)。
  - `conflict_unresolved` のPR(自分の push で head SHA が変わるまで再実行しない。main が進んだだけでは再試行しない)。
- サブエージェントの報告を受けるたびに、その結果をすぐ追記する(ラウンドの終わりまで待たない)。ラウンド数もここで数え、上限(10)の判定に使う。
- 最終報告はこのファイルの内容から作る。

注意:

- 同じ実行内で自分がコメントしただけのPR(マージ確認でマージせずコメントしたもの)は、作成者の新しいcommit・コメントがない限り、次のラウンドの対象にしない(「自分のコメント」は更新に数えない)。判定は手順 0c の状態ファイルの head SHA で行う。
- 同じ実行内で失敗したイシュー(テストが通らない等)は、次のラウンドでは再実行せず、報告に書く(状態ファイルの `failed`)。
- 実装で自分のPRを作っても、自分のPRはレビュー対象にもマージ対象にもならない(コンフリクトを解消した自分のPRのマージ、手順 2d だけは例外)。そのPRを前提とするイシューは「自分の前提待ち」のままなので、次のラウンドでも着手しない(最終報告の「次にやるとよいこと」に書く)。
- 最終報告は全ラウンド分をまとめて1回だけ書く(ラウンドごとの内訳が分かるようにする)。

## 1. 対象の特定

次の2つ(レビューと実装)は互いに独立なので、手順 2 でまとめて並列に起動する。

### 1a. レビュー待ちPRの特定

`/start-task` の手順 0 と同じ条件でレビュー対象PRを集める(`gh api user --jq .login` で自分のログイン名を取得し、`gh pr list --state open --limit 1000 --json number,title,author,headRefName,isDraft,reviewDecision,reviews,updatedAt` から、作成者が自分でない・ドラフトでない・自分がレビュー済みで以降更新がない、ではないものを選ぶ)。該当PRを `/start-task` の手順 0 と同じ基準で2種類に分ける。提案や確認はしない。

- **レビュー対象**: まだ自分がレビューしていないPR。手順 2a でレビューする。
- **マージ確認の対象**: 自分がレビュー済みで、その後に更新(新しいcommit、作成者のコメント)があるPR。手順 2c で、指摘の対応を確認し、マージ可能なら**確認なしでマージする**。

1a で集めたPRのうち、`status::pr-review` または `status::merge-check` が付いていて、`docs/kanban.md` の「他の人の作業中を避ける」の判定で他の人が作業中のものは、このラウンドの対象から外す(報告に書く)。

### 1b. 実装対象イシューの特定

`/start-task` の手順 1 の「依存関係の把握」までと同じ方法で、候補の分類を行う(`--limit 1000` を必ず付ける)。

1. `gh issue list --state open --assignee @me --limit 1000 --json number,title,author,labels,body,updatedAt` で自分が担当のオープンなイシューを取得する。`type::tracking` ラベルのものは除く。
   - 自分が担当のイシューが0件なら、担当者のいないオープンなイシューは**実装しない**。その旨を報告し、実装側(手順 2b)は行わない(レビュー・マージ確認は続ける)。
2. 各イシュー本文の `前提: #34、#38、...` の行から前提イシューを抜き出し(`親イシュー:` は依存ではない)、オープンかどうかを確認して「着手可能」「自分の前提待ち」「他の人待ち」に分類する。
3. **対象は「着手可能」なものすべて**。引数で番号が指定されたときは、その番号のうち「着手可能」なものだけを対象にする(指定されても、前提が未完了のものは対象外にして報告に書く)。
4. 実装対象が0件なら、分類結果(待っている前提と担当者)を状態ファイルの `skipped` に記録し、実装側(手順 2b)は行わない(レビュー・マージ確認は続ける。ループ全体の終了は手順 0b の条件で判定する)。
5. 対象の一覧(番号・タイトル・分類)を表示してから、そのまま続行する。

### 既存PRの確認

対象ごとに `gh pr list --state open --limit 1000 --json number,title,headRefName,closingIssuesReferences` で対応するオープンなPRを探す。

- PRがあり、レビューが投稿されている(`gh pr view <番号> --json reviews,comments` と `gh api repos/{owner}/{repo}/pulls/<番号>/comments`) → **レビュー対応モード**(`/start-task` の手順 3'・5 と同じ)。
- PRがあり、レビューがない → すでに対応中なので**スキップ**する(報告に書く)。
- PRがない → 通常モード。

### 1c. コンフリクトしている自分のPRの特定

`gh pr list --state open --author @me --limit 1000 --json number,title,headRefName,mergeable` で、`mergeable` が `CONFLICTING` の自分のPRを集める。`UNKNOWN` は GitHub が計算中なので、少し待って1回だけ取り直し、それでも `UNKNOWN` ならこのラウンドでは対象外にする。他の人のPRは対象外(他人のブランチは書き換えない)。

これは手順 2b のレビュー対応モードの対象PRにも当てはまる(対応前にコンフリクトを解消する。手順 2b の 6)。同じPRを手順 2d と 2b で二重に起動しない(レビュー対応モードで処理するPRは 2d の対象から除く)。

## 2. 並列で実行(レビューと実装)

レビュー対象PRごと・実装対象イシューごとに `Agent` ツールでサブエージェントを起動する。**独立した呼び出しは1回の応答にまとめて並列に起動するが、同時に動かすサブエージェントは最大4つまで**。対象が5つ以上ある場合は、4つずつのバッチに分け、バッチ内のサブエージェントがすべて完了してから次のバッチを起動する。順序はレビュー・マージ確認を先に、実装を後にする(マージで前提が解消され、状態が変わるため)。

### 2a. レビュー用サブエージェント(PRごと)

プロンプトには、PR番号と原則(質問しない・破壊的操作をしない)を含め、`.claude/commands/pr-review.md` の手順を、次のとおり読み替えて実行させる。

- 手順 1(対象PRの特定)は済んでいるので、渡されたPR番号を対象とする。
- 手順 2: worktree は `../opendopa-pr-<番号>`。既存があり未コミットの変更がなければ再利用、あれば別名にする。ユーザーには尋ねない。
- 手順 2 の前に、PR のラベルを `status::pr-review` にする(既存の `status::*` は同じコマンドで外す)。
- 手順 3: 同じ観点でレビューする。イシューが特定できなければ、PR説明欄と差分だけでレビューし、その旨をコメントに書く。決定記録の妥当性に迷う場合は、断定せず「確認してほしい点」として書く。
- 手順 4・5: ユーザーに提示・確認せず、**そのまま投稿する**。投稿種別は常に `gh pr review <番号> --comment`(承認も変更要求もしない。マージ可否の判断は人に残す)。行単位の指摘は `gh api` の行コメントで付けてよい。指摘がなければ「指摘なし」の旨と確認した内容を短く投稿する。日本語で書く。
- 投稿後、ラベルを付け替える。指摘を投稿したら `status::changes-requested`、「指摘なし」なら `status::ready-to-merge`。レビューが途中で失敗した場合は、`status::pr-review` を外して元に戻す(元のラベルがなければ外すだけ)。
- 手順 6: 変更がない(`git status --porcelain` が空)worktree とローカルブランチ `pr-<番号>-review` は削除する。起動した docker 等も削除する。
- 返してほしい報告: PR番号、投稿した指摘の要約、総評、テスト・lint の結果

### 2c. マージ確認用サブエージェント(PRごと)

プロンプトには、PR番号と原則(質問しない・破壊的操作をしない)を含め、次を実行させる。

- 最初に PR のラベルを `status::merge-check` にする。
- `/start-task` の手順 0 の「指摘の対応確認とマージ可否」に従い、自分の指摘がコードで対応されているかを確認し、マージ可否を判断する。worktree は `../opendopa-pr-<番号>`(手順 2a と同じ扱い)。
- **マージ可能なら、確認なしで** `gh pr merge <番号> --merge` でマージする。ブランチは削除しない。マージ後にクローズされたイシューを確認する。
- **マージ可能でなければ、マージしない。** 未対応の指摘が残っている場合は、未対応の点を `gh pr comment` で作成者に `@<ログイン名>` で伝える(「対応済みの確認結果」と「残っている指摘」を簡潔に)。競合・CI失敗は、事実のみコメントする。いずれも承認・変更要求はしない。マージしなかったときは、`status::merge-check` を `status::changes-requested` に付け替える(マージしたときはワークフローが外すので何もしない)。
- `gh pr merge` が権限判定(Claude Code の許可)で拒否された場合は、一時的な誤判定の可能性があるため、**同じコマンドをそのまま再試行する**(間隔をあけて最大3回)。再試行しても拒否される場合は、別のコマンド・API・設定ファイルの書き換えなどで回避せず、マージせずに「マージ可能と判断したが権限で拒否された」と報告して次へ進む。
- 判断に迷う場合(指摘への対応が部分的、対応しない理由の妥当性が微妙、など)は**マージしない**。理由を報告に書く。
- 後片付けは手順 2a の手順 6 と同じ。
- 返してほしい報告: PR番号、各指摘の対応状況、マージしたか(しなかった理由)、クローズされたイシュー

マージされたPRに依存するイシュー(手順 1b で「他の人待ち」「自分の前提待ち」としたもの)は、この実行では着手しない。最終報告の「次にやるとよいこと」に書く。

### 2d. コンフリクト解消用サブエージェント(自分のPRごと)

手順 1c のPRごとに起動する。プロンプトには、PR番号と原則(質問しない・破壊的操作をしない)を含め、次を実行させる。

- 最初に PR のラベルを `status::conflict` にする。元のラベル(`status::review-wait` など)は覚えておく。
- worktree を `../opendopa-<イシュー番号 or PR番号>` に用意する(既存があり未pushの変更がなければ再利用、あれば別名)。PRのheadブランチをチェックアウトする。
- `git fetch origin` のあと、`git merge origin/<デフォルトブランチ>` で取り込む。**rebase と force push はしない**(履歴を書き換えない)。
- コンフリクトを解消する。
  - `docs/DECISIONS.md` などの追記系は、両方の行を残す。
  - コード・スキーマは、双方の意図(PRの説明欄・イシュー・main側の該当 commit)を読んで統合する。生成物(`packages/shared/src/generated/` など)は手で直さず、元(JSON Schema)を統合して `mise run gen-types` で再生成する。
- `mise run lint` と `mise run test` を通す(web を変えたなら `pnpm typecheck` も)。
- 通ったら merge commit を `git push origin <ブランチ名>` で push する。コミットメッセージは日本語(例: `merge: main を取り込みコンフリクトを解消`)。PRへのコメントは、解消した内容を2〜3行で `gh pr comment` に書く。
- **push 後、次の条件をすべて満たせば、確認なしで自分のPRをマージする。** `gh pr view <番号> --json mergeable,reviewDecision,statusCheckRollup` で確認する(`mergeable` が `UNKNOWN` なら少し待って1回だけ取り直す)。
  - `mergeable` が `MERGEABLE`(解消後に再びコンフリクトしていない)。
  - 解消のためのマージで、コンフリクトの解消以外のコード変更を加えていない(指摘対応などの別の変更が混ざっていない)。
  - `reviewDecision` が `CHANGES_REQUESTED` ではない(変更要求が残っていない)。レビュアーの未対応の指摘が残っていないことも `gh pr view <番号> --json reviews,comments` で確認する。
  - CI があるときは、すべて成功している(実行中なら終わるまで待つ。失敗なら事実だけコメントしてマージしない)。
  - ローカルの `mise run lint` と `mise run test` が通っている。
- マージは `gh pr merge <番号> --merge`(ブランチは削除しない)。マージ後、`Closes #N` のイシューがクローズされたことを確認する。権限判定で拒否された場合の扱いは手順 2c と同じ(同じコマンドを最大3回再試行し、それでも拒否されたら回避せず「マージ可能と判断したが権限で拒否された」と報告する)。
- 条件を1つでも満たさない場合、判断に迷う場合は**マージしない**。理由を報告に書く(レビュアーがいるときは、再レビューが必要かを一言添えてコメントする)。
- **解消できない・判断に迷う場合は push しない。** `git merge --abort` で元に戻し、コンフリクトしたファイルと理由(双方の意図が両立しない、など)を報告する。PRには事実だけを短くコメントしてよい。
- 終わったら `status::conflict` を、覚えておいた元のラベルに付け替える(元がなければ外す)。解消できなかった場合も同じ。マージしたときはワークフローが外すので何もしない。
- 後片付けは手順 3 の実装用 worktree と同じ。
- 返してほしい報告: PR番号、コンフリクトしたファイルと解消方針、push した commit、テスト結果、マージしたか(しなかった理由)、クローズされたイシュー、解消できなかった場合の理由

### 2b. 実装用サブエージェント(イシューごと)

各サブエージェントには、次をプロンプトに含める。

- イシュー番号、この `sleep` の原則(質問しない・他人のPRに投稿しない・破壊的操作をしない)
- 作業対象は自分の worktree だけで、メインの作業ディレクトリでは `git checkout` / `git switch` をしないこと
- 以下の手順(各イシューで独立)
  1. `/start-task` の手順 1 の末尾に従い `gh issue view <番号>` で要求を把握する。不明点があっても質問せず、最も妥当な解釈で進め、解釈を PR 説明欄の「決めたこと」に書く。
  2. `/start-task` の手順 2 に従い worktree を作成する(`git fetch origin` 後、`git worktree add -b <prefix>/<番号>-<description> ../opendopa-<番号> origin/<デフォルトブランチ>`)。同名のworktree・ブランチが既にある場合は、内容を確認し、未pushの変更がなければ再利用、あれば新しい名前(`-2` など)で作る。worktree を作る前に、通常モードではイシューに `status::in-progress` を付ける。レビュー対応モードでは PR を `status::fixing` にする(既存の `status::*` は同じコマンドで外す)。
  3. `/start-task` の手順 3・3a に従い実装する(CLAUDE.md の約束とテスト・lint、決定の記録を含む)。`mise run lint` と `mise run test` を通す。web を変えたら `cd apps/web && mise exec -- pnpm typecheck` も通す。
  4. `/start-task` の手順 4 の self-review を、指摘がなくなるまで(最大3回)自律的に繰り返す。
  5. 意味のある単位で commit し(CLAUDE.md の書き方どおり日本語、既存の履歴の形式)、`git push -u origin <ブランチ名>` し、`gh pr create` で PR を作成する(`Closes #<番号>`、変更概要、self-review の結果、テスト結果、決めたこと、を説明欄に書く)。作成したら、イシューの `status::in-progress` を外し、PR に `status::review-wait` を付ける。
  6. レビュー対応モードの場合は、worktree でPRのheadブランチを使い、まず `git fetch origin` して `origin/<デフォルトブランチ>` との差分を確認する。PRが `CONFLICTING` なら、手順 2d と同じ方法(merge。rebase・force push はしない)でコンフリクトを解消してから、指摘に対応する。解消できない場合は、対応報告にその旨を書く。修正したら push したうえで、**確認なしで**レビュアーに `@<ログイン名>` で対応報告を `gh pr comment` する(対応内容・commit ハッシュ・対応しなかった指摘と理由・再レビューのお願い)。報告したら `status::fixing` を `status::review-wait` に付け替える。対応できず終えた場合も `status::fixing` は外す(`status::changes-requested` に戻す)。
- 返してほしい報告: PR の URL、実装の要約、記録した決定事項、self-review で直した点、未解決事項、起動した docker 等の一時リソース、worktree のパス

サブエージェント同士が同じファイル(`docs/DECISIONS.md` の末尾など)を編集してマージ時に衝突しうることは想定済み。衝突は後でマージする人が解決するので、事前に調整しようとしない。ただしその旨を最終報告に書く。

## 3. 後片付け

全サブエージェントの完了後、確認なしで次の後片付けを行う。

- レビュー用 worktree は手順 2a で削除済みのはずなので、残っていれば報告する。
- 実装用 worktree: 変更がすべて commit・push 済み(`git -C ../opendopa-<番号> status --porcelain` が空で、`git log origin/<ブランチ名>..HEAD` も空)のものだけ `git worktree remove ../opendopa-<番号>` で削除する。そうでないものは残し、報告に書く。
- 実装中に起動した捨て docker コンテナ・ボリューム・ネットワークのうち、サブエージェントが自分で起動したと報告したものだけ削除する。それ以外には触れない。
- ブランチは削除しない(PR が参照している)。

## 4. 最終報告

次をまとめて報告する(ユーザーが朝に読む前提で、簡潔に)。

- レビューした PR の表(PR の URL・作成者・指摘の要約・総評)
- マージ確認した PR の表(PR の URL・作成者・各指摘の対応状況・マージしたか、しなかった理由)
- 作成・更新した PR の表(イシュー番号・PR の URL・モード・テスト結果)
- コンフリクトを扱った自分の PR の表(PR の URL・コンフリクトしたファイル・解消方針・push したか・マージしたか、解消できなかった理由・マージしなかった理由)
- スキップ・対象外にしたイシューとその理由(待っている前提と担当者、既存PRで対応中、など)
- 質問せずに自分で判断した点
- 未解決事項、残した worktree、マージ時に衝突しそうな箇所
- 次にやるとよいこと(今回の PR がマージされると着手可能になるイシューなど)

# タスク開始

引数: `$ARGUMENTS`(イシュー番号。省略可)

以下の手順を順に実行する。

## 00. main の最新化(最初に必ず実行)

他の手順より前に、メインの作業ディレクトリで main を最新にする。コマンド定義(`.claude/commands/`)も main に含まれるため、これで常に最新の手順で動く。

- `git status --porcelain` と `git branch --show-current` を確認する。
- 現在のブランチが main で、未コミットの変更がなければ `git pull --ff-only origin main` を実行する。
- 現在のブランチが main 以外、または未コミットの変更がある場合は、`git checkout` / `git switch` をせず、`git fetch origin` だけを行い、main を更新できなかった旨を伝える(以降の worktree は `origin/main` を起点にするので問題ない)。
- `--ff-only` で失敗した場合(ローカルの main が分岐している等)は、無理に merge / reset せず、その旨を伝える。
- pull で `.claude/commands/` の内容が変わった場合は、このコマンドの定義を読み直し、最新の内容に従って以降を実行する。

## 0. レビュー待ちPRの確認

タスクに着手する前に、他の人が作成したレビュー待ちのPRがないかを確認する。

- `gh api user --jq .login` で自分のログイン名を取得する。
- `gh pr list --state open --limit 1000 --json number,title,author,headRefName,isDraft,reviewDecision,reviews,updatedAt` でオープンなPRを取得し(`gh` の一覧は既定で30件しか返さないため、`--limit` を必ず付ける)、次の条件で絞り込む。
  - 作成者が自分ではない。
  - ドラフトではない(`isDraft` が false)。
  - 自分が既にレビュー済みで、その後に更新がない、というものは除く(`reviews` の自分の投稿日時と `updatedAt` で判断する)。
- 該当PRを次の2種類に分ける。
  - **マージ確認の対象**: 自分がレビューを投稿済みで、その後に更新(新しいcommit、作成者のコメント)があるPR。指摘が対応されたかを下の「指摘の対応確認とマージ可否」で確認する。
  - **レビューの対象**: 上記以外(まだ自分がレビューしていないPR)。
- 該当PRがある場合:
  - 番号・タイトル・作成者・ブランチ・更新日時・レビュー状況・種類(マージ確認/レビュー)をMarkdownテーブルで表示する。
  - 種類ごとに提案し、ユーザーの回答を待つ。
    - レビュー対象 → `/pr-review <番号>` でのレビューを提案する。レビューする場合は `/pr-review` の手順に従う(完了後、タスク着手に進むかユーザーに確認する)。
    - マージ確認の対象 → 先に「指摘の対応確認とマージ可否」を実行し、結果(対応済みか、マージ可能か)を示したうえで、マージを提案する。許可が出たらマージする。未対応の指摘が残っていれば、マージではなく再レビュー(`/pr-review`)を提案する。
    - 後回しにする・不要 → そのまま手順1へ進む。
  - ユーザーの許可なしにレビューを開始したり、コメントを投稿したり、マージしたりしない。
- 該当PRがなければ、何も言わずに手順1へ進む。

### 指摘の対応確認とマージ可否

マージは、レビューした人(自分)が行う。自分のレビュー後に更新されたPRについて、次を確認する。

1. `gh pr view <番号> --json reviews,comments,commits,mergeable,mergeStateStatus,reviewDecision,statusCheckRollup,isDraft` と `gh api repos/{owner}/{repo}/pulls/<番号>/comments` で、自分が投稿した指摘(レビュー本文・行コメント)を一覧にする。
2. 自分の最後のレビュー以降のcommitと作成者の返信を読み、`gh pr diff <番号>` で、各指摘が実際にコードで直っているかを確認する(返信の文面だけで判断しない)。対応しないという返信がある指摘は、理由が妥当かを判断する。
3. 次をすべて満たすとき「マージ可能」とする。
   - 自分の指摘がすべて対応済み、または対応しない理由が妥当。
   - 必要ならworktreeでテスト・lintが通る(`/pr-review` の手順2のworktreeを使い、確認後は後片付けする)。
   - `statusCheckRollup` に失敗がない(CIがなければ問わない)。
   - `mergeable` が `CONFLICTING` でない。ドラフトでない。他のレビュアーの変更要求が残っていない。
4. マージ可能でなければ、理由(未対応の指摘、競合、CI失敗など)を伝える。
5. マージは `.claude/shared/merge-rules.md` に従って行う。マージ後、前提が解消されて着手可能になったイシューがあれば手順1に反映する。

## 1. 対象イシューの特定

- `gh issue list` は既定で30件しか返さない。**必ず `--limit 1000` を付ける**(以降の `gh issue list` / `gh pr list` も同様)。
- 自分が担当のオープンなイシューを取得する:
  `gh issue list --state open --assignee @me --limit 1000 --json number,title,author,labels,body,updatedAt`
  - `[追跡]` イシュー(ラベル `type::tracking`)は実装対象ではないので候補から除く。
  - 自分が担当のイシューが0件のときは、その旨を伝え、担当者のいないオープンなイシュー(`gh issue list --state open --limit 1000 --json number,title,assignees,labels,body,updatedAt` を取得し、`jq` で `assignees` が空のものに絞る)を候補として提示してよいか尋ねる(他の人の担当分は候補にしない)。
- **依存関係の把握**: 各イシュー本文の冒頭にある `前提: #34、#38、...` の行から、前提イシューの番号を抜き出す(`親イシュー:` は依存ではないので除く。本文に「前提」の記載がなければ依存なしとする)。
  - 前提イシューのうち、まだオープンなものを `gh issue list --state open --limit 1000 --json number,title,assignees,labels` の結果と突き合わせて特定する(クローズ済みは解消済みとみなす)。
  - 前提がオープンの場合、その担当者を確認し、次のように分類する。
    - **着手可能**: 前提がすべてクローズ済み。
    - **自分の前提待ち**: オープンな前提がすべて自分の担当(先にそちらを終わらせれば着手できる)。
    - **他の人待ち**: オープンな前提に、他の人が担当のもの、または担当者なしのものがある(その作業が終わるまで着手できない)。
- 引数が空、または指定番号のイシューが担当分の候補にない場合:
  - 候補が1件のみ → それを自動で選択する(ただし「他の人待ち」ならその旨を伝え、続行してよいか確認する)。
  - 2件以上 → 番号・タイトル・作成者・ラベル・更新日時・状態(着手可能/自分の前提待ち/他の人待ち)・オープンな前提をMarkdownテーブルで表示する。
    - 「他の人待ち」のイシューには、待っている前提イシューの番号とその担当者(`@login`、未担当なら「未担当」)を明記する。
    - テーブルの後に、**いま一番やるべきタスクを1つ提案**し、理由を添える。選び方は次の順:
      1. 「着手可能」なものから選ぶ(「他の人待ち」は選ばない)。
      2. 他のイシューの前提になっている数が多いもの(これを終えると他の人や自分の作業が解放される)を優先する。
      3. 同程度なら、ラベル `priority: high` > `medium` > `low` の順。
      4. それでも並ぶなら、番号が小さいもの。
    - 着手可能なものがなければ、「自分の前提待ち」のうち先に片付けるべき前提イシュー(担当が自分のもの)を提案する。それもなければ、すべて他の人待ちである旨と、待っている相手を伝える。
    - 提案を示したうえで、ユーザーに番号を尋ねて待機する(存在しない番号を指定された場合はその旨も伝える)。
  - 0件 → その旨を伝えて終了する。
- 引数で番号が明示された場合は、担当者に関係なくそのイシューを対象とする(オープンであること。他の人が担当なら、その旨を伝えて続行してよいか確認する)。前提が「他の人待ち」の場合も、その旨と相手を伝えて続行してよいか確認する。
- `gh issue view <番号>` で要求事項・タスクを把握する。不明点が実装に影響する場合はユーザーに尋ねる。

### 既存PRとレビューの確認(モード判定)

- `gh pr list --state open --limit 1000 --json number,title,headRefName,closingIssuesReferences` で、対象イシューに紐づくオープンなPR(`closingIssuesReferences` に含まれる、またはPR説明欄・ブランチ名 `<prefix>/<番号>-...` で対応が確認できるもの)を探す。
- 該当PRがある場合、`gh pr view <PR番号> --json reviews,comments` と `gh api repos/{owner}/{repo}/pulls/<PR番号>/comments`(行コメント)でレビューを確認する。
  - **レビューが投稿されている** → **レビュー対応モード**。手順3の「実装」の代わりに、手順3'「レビュー指摘の修正」を行う。手順5はpushのみ(PRは新規作成しない)。
  - レビューがない → 通常モード(PRが既にある旨をユーザーに伝え、続行してよいか確認する)。
- 該当PRがない場合 → 通常モード。

## 2. worktree ブランチの作成

進行中の他作業を壊さないため、現在の作業ディレクトリでは `git checkout` / `git switch` を行わない。

- **レビュー対応モード**: 新規ブランチは作らず、PRのheadブランチを使う。`git fetch origin <headRefName>` 後、`git worktree add ../opendopa-<イシュー番号> <headRefName>`(ローカルブランチがなければ `-b <headRefName> origin/<headRefName>`)で作成する。以降の箇条書き(ブランチ命名・起点)は通常モードの説明。
- ブランチ名は次の規則に従う: `<prefix>/<issue-number>-<description>`
  - `prefix` は `feat` / `fix` / `refactor` など(イシューの内容から選ぶ)。
  - `description` は英小文字とハイフンの短い説明。
  - 例: `feat/18-add-login-api`, `fix/28-auth-error`, `refactor/35-clean-user-service`
- `git fetch origin` 後、デフォルトブランチ(`origin/main` 等)を起点に作成する:
  `git worktree add -b <ブランチ名> ../opendopa-<イシュー番号> origin/<デフォルトブランチ>`
- 既に同名のworktree・ブランチがある場合は、内容を確認してから再利用するかユーザーに尋ねる。
- 以降のファイル編集・テスト実行などはすべてこのworktree内で行う。
- 状態ラベル(`docs/kanban.md`)を付ける。通常モードはイシューに `status::in-progress`、レビュー対応モードはPRに `status::fixing`(既存の `status::*` は同じコマンドで外す)。

## 3. 実装

- イシューの要求事項・タスクを満たすよう、worktree内で実装する。
- 既存のコード規約・構成に従い、必要なテストも追加する。
- テストやlintが存在すれば実行して通ることを確認する。後片付けが必要になるもの(捨てdockerコンテナ等)を起動した場合は、何を起動したか記録しておく。
- 実装中に決めたこと(設計書・イシューの既定値から外れた判断、複数の選択肢から選んだこと)は、後から理由が分かるよう、手順3aに従って記録する。

## 3a. 決定事項の記録(ADR / DECISIONS.md)

実装・レビュー対応の中で決めたことは、`.claude/shared/decision-record.md` に従って記録する(記録は実装と同じcommit・同じPRに含める)。

## 3'. レビュー指摘の修正(レビュー対応モードのみ。手順3の代わり)

- 未解決のレビュー指摘(レビュー本文・行コメント・通常コメント)を一覧化し、ファイル・行・内容ごとに整理する。
- 各指摘をworktree内で修正する。指摘が誤り・不適切だと判断できる場合や、修正方針が複数ありうる場合は、勝手に無視せず、最終報告で理由とともにユーザーに伝える。
- 必要ならテストを追加・更新し、テスト・lintを実行して確認する。
- 修正の過程で決めたこと(指摘への対応方針の選択など)があれば、手順3aに従って記録する。

## 4. self-review(同一ブランチで実施)

実装後、`git diff origin/<デフォルトブランチ>...HEAD`(未コミット分を含む)と worktree 上のコードを読み、以下の観点でレビューする。

1. **要件充足**: イシューの要求事項・タスクを満たしているか。
2. **正確性**: 実装のバグ、考慮漏れ、明らかなミスがないか。
3. **簡潔さ**: 冗長なコード、不要な抽象化、無駄なコメント、長すぎる変数名がないか。
4. **テスト**: 必要なテストが追加されているか。
5. **決定の記録**: 実装中に決めたことが、ADR または `docs/DECISIONS.md` に漏れなく書かれているか。ADR を追加したなら一覧表も更新されているか。記録と実装・設計書が食い違っていないか。

- 推測だけで指摘しない。コードで確認できた問題に絞る。
- 指摘があれば、ユーザーに確認せず自律的に同じブランチ上で修正する。
- 修正後はテスト・lintを再実行し、再度レビューする。指摘がなくなるまで繰り返す(目安: 最大3回。それでも残る場合は最終報告に明記する)。

## 5. commit と PR 作成

**レビュー対応モード**: 修正をcommitして既存PRのブランチへ `git push` する(PRは新規作成しない)。pushしたら `status::fixing` を `status::review-wait` に付け替える(`docs/kanban.md`)。commitメッセージは対応した指摘が分かるようにする。その後、レビュー指摘への対応が完了したことをユーザーに通知する(指摘ごとの対応内容、対応しなかった指摘とその理由、self-reviewの結果を含める)。続けて、レビュアーへの対応報告をPRに投稿する。

- 報告先: 指摘を投稿したレビュアー(`gh pr view <PR番号> --json reviews,comments` と行コメントの投稿者。自分自身とbotは除く)を `@<ログイン名>` 形式でメンションする。
- 文面: 対応した旨、指摘ごとの対応内容(commitのハッシュを添える)、対応しなかった指摘とその理由、再レビューのお願いを簡潔に書く。
- 投稿は `gh pr comment <PR番号> --body ...` で行う。行コメントへの返信が適切な指摘は `gh api` で該当コメントに返信してもよい。
- **投稿前に文面とメンション先をユーザーに提示し、許可を得る。** 許可なしにPRへコメント・返信を投稿しない。

その後、手順6を提案する。

**通常モード**:

- 変更内容を意味のある単位でcommitする。メッセージは既存の履歴の形式(例: `feat: ...` / `fix: ...`)に揃える。
- `git push -u origin <ブランチ名>` でpushする。
- `gh pr create` でPRを作成する。作成したら、イシューの `status::in-progress` を外し、PRに `status::review-wait` を付ける(`docs/kanban.md`)。
  - タイトルはcommitと同じ形式で簡潔に。
  - 説明欄に変更概要、self-reviewの結果、テスト結果を書き、`Closes #<イシュー番号>` を含める。
  - 決定事項を記録した場合は、「決めたこと」の節に要点を箇条書きし、ADRへのリンクを添える。
  - ベースブランチはデフォルトブランチ。

## 6. 完了報告と後片付け

- PRのURL、実装内容の要約、記録した決定事項(ADR・DECISIONS.md)、self-reviewで修正した点、未解決事項を報告する。
- 以下の後片付けを提案する。
  - 作成した worktree(`git worktree remove ../opendopa-<イシュー番号>`)
  - 実装中に起動した捨てdockerコンテナ・ボリューム・ネットワーク等
  - その他の一時ファイル
- 削除対象の一覧を示し、**ユーザーの許可を得てから**削除する。未コミット・未pushの変更がある場合は、削除前に警告する。

# ハーネスの自己改善

/sleep 自身の仕組み(手順書・スクリプト)の不具合や改善点を、/sleep が自分で直すときの手順。アプリのコードには広げない。

## 触ってよい範囲

機械的に決める。PR の変更ファイルが**許可**の外にあれば、自己改善としては扱わない(`needs-human` を付けて報告する)。

| | パス |
| --- | --- |
| 許可 | `.claude/commands/sleep.md`、`.claude/sleep/*.md`、`.claude/shared/*.md`、`mise-tasks/sleep-scan`、`docs/kanban.md`、`docs/decisions/*.md` |
| 禁止(直さず報告だけ) | `.claude/settings.json`(権限)、認証・秘密の値、`.github/workflows/`、アプリのコード(`apps/` `services/` `pipeline/` `packages/` `db/`) |

許可リスト内のファイルでも、**原則**(質問しない・破壊的操作をしない・投稿とマージの範囲・REST のみ)を緩める変更は、自己改善として扱わず `needs-human` にする。

## 手順(PR 方式)

1. **検知**: 失敗(スクリプトのエラー、サブエージェントが手順書どおりに進められなかった、同じ対象が空回りした)に気づいたら、症状・原因・どの手順書のどこかを短くメモする。同じ失敗が2回出たものと、1回でも作業が止まったものは直す。
2. **修正**: `fix/harness-<slug>` ブランチを main から切り、最小の変更で直す。ついでの整理はしない。
3. **PR**: 本文は「症状 → 原因 → 修正 → どう確かめたか」。確かめ方は、実際に `sleep-scan` を実行する、手順書どおりに1回通す、など。
4. **セルフレビュー**: 書いた本人とは別のサブエージェントに、差分とこのファイルだけを渡して見せる。観点は次のとおり。
   - 変更が許可の範囲に収まっているか。
   - 症状に対する修正になっているか(原因を直しているか、症状を隠していないか)。
   - 既存の原則(質問しない・破壊的操作をしない・投稿してよい範囲・REST のみ)を弱めていないか。
   - 他の手順書と矛盾していないか(同じ規則を複数の場所に書いていないか)。
5. **マージ**: 自己修復の PR は、作成者以外のレビューが付かないため、自動マージ(`automerge-ready.yml`)の条件を満たせない。そこで `/sleep` が自分でマージする(`sleep.md` のマージの枠(4))。条件は `merge-rules.md` に従う(CI の必須チェックが成功、`mergeable_state` が `clean`、`sha` を付ける)。権限で拒否されたら、`merge-rules.md` のとおり再試行し、それでも拒否されたら回避せず報告する。セルフレビューの指摘があれば直して再レビュー。**2周で通らなければ `needs-human`**。
6. 最終報告に、直した内容と PR を書く。

## 直接 push してよい例外

main が壊れていて、PR の CI が回せないときだけ。それ以外は PR にする。force push はしない。

## 環境メモ

- `git fetch` / `git push` が SSH で失敗するときは `git -c credential.helper='!gh auth git-credential' <fetch|push> https://github.com/<R>.git ...` を使う(設定は変えない)。

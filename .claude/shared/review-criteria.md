# レビューの観点

`/pr-review` と `/sleep` のレビュー用サブエージェントが共通で使う。`gh pr diff <番号>` と worktree 上のコードを読み、次の5観点で見る。

1. **要件充足**: イシューの要求事項・タスクを満たしているか。
2. **正確性**: 実装のバグ、考慮漏れ、明らかなミスがないか。
3. **簡潔さ**: 冗長なコード、不要な抽象化、無駄なコメント、長すぎる変数名がないか。
4. **テスト**: 必要なテストが追加されているか。
5. **決定の記録と設計書・方針との整合**: 設計書(`docs/design_doc.md` など)・イシューの既定値・方針から外れた実装がないか。
   - 外れていても、`.claude/shared/decision-record.md` に沿った妥当な決定記録(`docs/adr/` のADR、または `docs/DECISIONS.md` の「小さな決定」)がPRに含まれていれば**許可する**(指摘しない)。
   - 記録の妥当性は、理由が具体的か、他の決定・設計書と矛盾しないか、規模に見合う書き先か(大きな決定はADR、小さな決定は `DECISIONS.md`)、ADRなら `docs/DECISIONS.md` の一覧表も更新されているか、設計書と食い違う場合は設計書も更新されているか、で判断する。
   - 外れているのに記録がない、または記録があっても理由が不十分・矛盾している場合は指摘する。修正案は「記録を追加する」か「方針に合わせて実装を直す」のどちらが妥当かを示す。

## 共通の注意

- 推測だけで指摘しない。コードで確認できた問題に絞る。
- 指摘がない観点は、その旨を一言添える。
- `CLAUDE.md` の約束(DB の境界、実行時に LLM を呼ばない、生成物を手で編集しない、など)を破っていないかも見る。

## テスト・lint を実行するかの判断(worktree のコスト削減)

worktree は毎回まっさらで、`pnpm install` や `cargo build` がキャッシュなしで走るため高くつく。次の順で判断する。

- 差分が文書・コメント・設定の追記だけ(`docs/`、`*.md` など) → worktree を作らず、`gh pr diff` だけでレビューする。
- `statusCheckRollup` で、PRの head に対する CI がすべて成功している → テスト・lint は再実行しない(CI の結果を使う)。
- それ以外 → worktree を作り、**差分が触れた言語・ディレクトリの範囲だけ**を実行する(Python だけなら pipeline のテストと lint、など)。全言語の `mise run lint` / `mise run test` は、差分が複数言語にまたがるときだけ。
